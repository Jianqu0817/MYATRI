# 最早记忆读取修复（0.2.0 补丁）

用户反馈在私聊中询问最开始的记忆时，角色把“索引水位落后”理解为无法读取旧记忆，群聊也复述了这种说法。现场核查发现原始版本记录完整；私聊基础索引落后于档案37次提交，群聊基础索引也有新增消息尚未覆盖。原有检索仍有档案扫描及增量回退，不等于原文丢失。

另一个已复现的问题是，“最早我们聊了什么”没有具体内容关键词，词面/向量容易先找到后来反复讨论初识的内容。ATRI历史经历两次迁移后，原始消息还会处于嵌套的human_import记录中。

本次修复：

- 对明确询问最早认识/聊天/记忆的查询，按原始记录时间优先定位最早4条保留的对话。只沿显式human_import来源包装查找，可处理两次迁移；不把模型自述当原始聊天。
- 继续遵守当前快照、人物候选及时间筛选。明确询问“群里最早”时不拿迁入私聊冒充本群发言。
- 超长原文保留精确版本定位，可用read_record分页；最早保留的记录不能证明现实中第一次认识。
- 更正运行提示：索引/FTS维护信息、未启用激活，都不表示记忆不存在。查不到与确认不存在须区分。
- 在本机重建小温暖私聊、旧ATRI及当前群的索引，保留旧索引世代与重建前current指针。核对原始记录与人格未被改写，无LLM调用、无微信发送。

实际重建水位：小温暖私聊438、旧ATRI328、当前群193；分别保留534、413、781条原始版本记录。用户可继续聊天，因此之后水位增加属于正常情况。

真实本机库离线验证：三种“最早/最开始/第一次聊天”问法在三个库中均找到4条早期来源，原文分页均可读取。报告位于桥接项目本机 `var/diagnostics/earliest-memory-recovery-20261021.json`；这不是模型回答准确率测试。

回归验证：修复后的检索、早期历史及分页相关31项测试通过，桥接完整160项测试通过，改动代码Ruff通过。核心冻结wheel、实际安装及两份锁文件重新核对一致。群聊随机回复同步调整为10%，关键词与@触发不变。

可重复使用的本机修复命令（在主项目执行，不需要API）：

```powershell
.venv/Scripts/python.exe scripts/repair_memory_index.py --root var/xiaowennuan
.venv/Scripts/python.exe scripts/repair_memory_index.py --root var/myatri-main
```

群聊使用同脚本，显式传目标群目录、`--agent xiaowennuan --user group`；已有BGE模型时用`--model-path`指定本机模型目录。脚本要求既有匹配档案，不会创建一个空记忆库充当修复。

旧进程仍持有旧代码和内存索引。请退出并重新打开命令行聊天；群聊关闭旧机器人启动窗口，重新运行相邻项目的Start-WeChat-Live.cmd，微信可保持登录。没有自动重启服务，也没有commit/push。
